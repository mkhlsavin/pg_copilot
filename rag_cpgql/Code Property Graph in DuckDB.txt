Реализация Code Property Graph в DuckDB: плюсы, минусы и применение для RAG-анализа кода
Обзор: Code Property Graph и DuckDB (SQL/PGQ)
Code Property Graph (CPG) – это графовое представление программы, объединяющее абстрактное синтаксическое дерево (AST), граф потока управления (CFG) и граф зависимостей данных (PDG) внутри единой структуры[1]. Изначально CPG создавался для поиска уязвимостей в системном коде на C/C++[2], но впоследствии нашёл применение во многих задачах анализа кода: от обнаружения дубликатов и атакуемых поверхностей до генерации эксплойтов и оценки тестопригодности кода[2]. Благодаря объединению разных представлений кода, CPG позволяет одним запросом связно анализировать синтаксис, управление и потоки данных программы[3].
DuckDB с расширением DuckPGQ поддерживает стандарт SQL:2023 для графовых запросов (SQL/PGQ)[4]. В DuckDB граф представляется как property graph, заданный вершинами (таблицы узлов) и рёбрами (таблицы связей) с метками и свойствами. Это даёт возможность работать с графом через знакомый SQL-интерфейс с новым клаузами CREATE PROPERTY GRAPH и MATCH для шаблонов графа[5][6].
Сценарий RAG (Retrieval-Augmented Generation) с LLM в контексте ассистента по коду предполагает, что Large Language Model может выполнять структурированные запросы к базе знаний (в данном случае – базе CPG), чтобы получать факты о коде, и на их основе формировать ответы. Ниже рассмотрим, облегчит ли реляционная реализация CPG такой анализ, какие запросы можно выполнять с помощью SQL/PGQ (и насколько это эффективнее CPGQL), а также плюсы, минусы и дополнительные возможности данного решения.
1. Реляционный CPG в DuckDB для RAG: упрощает ли анализ кода?
Интеграция CPG в реляционную БД (DuckDB) существенно упрощает графовый анализ кода в сценариях с RAG. Во-первых, появляется возможность использовать стандартизированный язык SQL/PGQ вместо уникального DSL. Ранее графовые СУБД предлагали разные языки (Cypher, Gremlin, GSQL и др.), что приводило к фрагментации[7]. Стандарт SQL/PGQ устраняет этот разнобой, позволяя унифицированно “видеть графы в таблицах”[8]. Для LLM это означает, что запросы к коду можно формулировать на распространённом языке SQL (с понятным расширением для графов), вместо специфичного CPGQL. Большие модели лучше знакомы с SQL, поэтому им проще генерировать корректные запросы. Таким образом, снижается барьер для подключения LLM к анализу кода – разработчики могут заложить шаблоны SQL-запросов, или даже сам LLM сможет составлять их по естественно-языковому вопросу.
Во-вторых, DuckDB – аналитическая колоночная СУБД, обеспечивающая высокую производительность на больших объёмах данных. Исследования показали, что современные графовые БД заметно уступали реляционным системам по скорости на аналитических запросах по крупным графам (когда тот же запрос можно выразить на SQL)[9]. Используя DuckDB, мы наследуем её оптимизации: сжатие колонок, векторизированное выполнение запросов, параллелизм и эффективные джоины[10][4]. Это особенно актуально для больших баз кода – граф кода может содержать миллионы узлов (функций, выражений и пр.), и возможность выполнять сложные запросы за разумное время критична. Реляционный движок способен обрабатывать такие графовые выборки эффективно и масштабируемо[11][12], что подтверждают прототипы DuckPGQ.
В-третьих, хранение CPG в DuckDB облегчает интеграцию с другими данными и инструментами. DuckDB встраивается в приложения и поддерживает Python, R, C++ и др. Это значит, что LLM-ассистент может работать в единой среде: выполнять SQL/PGQ-запрос к DuckDB, получать результаты (таблицы, которые легко обработать Pandas/Numpy), и затем использовать их в контексте ответа. Такой плавный рабочий процесс (например, jupyter-ноутбук, где LLM агент формирует SQL-запрос и сразу получает ответ) повышает интерактивность разработки[13]. В отличие от этого, при использовании внешней CPG-платформы (например, Joern + Neo4j/OverflowDB) потребовалась бы отдельная инфраструктура и, возможно, конвертация данных. Реляционная реализация же позволяет держать базу кода рядом с остальными данными (в том числе embedding’ами функций, документацией и т.д.) и комбинировать их в запросах. Например, можно связать результаты графового анализа с векторным поиском по embedding – всё средствами одной СУБД.
Вывод: представление CPG через таблицы DuckDB упрощает анализ графа кода в RAG-сценарии за счёт стандартизации запроса (SQL), высокой производительности и удобной интеграции. LLM может эффективно извлекать из такой базы необходимые факты о коде – начиная от простых связей (кто вызывает эту функцию?) до сложных зависимостей – без глубокого погружения в исходный код. Это позволяет сконцентрироваться на логике ответа, делегируя поиск и фильтрацию данных СУБД.
2. Запросы к коду на SQL/PGQ и сравнение с CPGQL
Типы запросов, реализуемых через SQL/PGQ, охватывают практически все типичные задачи статического анализа, которые решаются на CPG. Стандарт SQL/PGQ вводит клаузу MATCH для шаблонного поиска путей в графе, аналогично языкам вроде Cypher[6][14]. Ниже перечислены ключевые категории запросов и примеры, а также комментарий об их выразительности и эффективности по сравнению с аналогами на CPGQL (DSL от Joern/ShiftLeft):
• Поиск по синтаксическому дереву (AST-паттерны): с помощью SQL/PGQ можно находить узлы AST определённого типа и отношения вложенности. Например, запрос может найти все вызовы функции strcpy с константным аргументом-литералом. В SQL/PGQ это выразится как MATCH-шаблон, связывающий узел типа CALL с дочерним узлом-аргументом типа LITERAL. В CPGQL/Joern есть похожие запросы (e.g. cpg.call("strcpy").argument.isLiteral), но LLM с SQL справится проще – достаточно описать нужные таблицы/метки в MATCH. Выразительность: SQL/PGQ покрывает такие шаблоны не хуже, используя понятия вершин с метками и ребер AST. Эффективность: DuckDB может быстро просканировать необходимые таблицы, используя индексы по типам узлов, и соединить их по связям AST. Это сопоставимо или быстрее спец. графовых движков, т.к. колоночное хранение и векторизация ускоряют поиск по свойствам узлов[12].
• Запросы по графу вызовов и зависимостям типов: CPG включает граф вызовов (CallGraph) и информацию о типах/классах. Например, запрос «найти все функции, вызывающие dangerous_function() и принадлежащие классу NetworkManager» требует сочетания отношений: узел-метод с именем dangerous_function и ребра вызова, а также проверку типа (CLASS или принадлежность к классу). В SQL/PGQ можно составить MATCH с двумя шаблонами: один найдёт метод-мишень по имени, другой – путь от некоторого метода-источника к мишени по ребру CALLS, плюс условие на свойство класса источника. В CPGQL подобный запрос тоже возможен (Joern DSL позволяет .caller и фильтрацию по свойствам), но с SQL/PGQ это выполняется в едином стандартизованном синтаксисе. Эффективность: DuckDB способна выполнять такие многошаговые соединения за счёт оптимизированных джоинов. Примечание: SQL/PGQ поддерживает поиск путей произвольной длины (регулярные пути) для задач графа вызовов – например, найти транзитивные вызовы (цепочки) функции, что эквивалентно рекурсивному запросу. Это встроено в стандарт (паттерны с * или функции path-finding), тогда как в CPGQL возможно потребует рекурсивный обход вручную.
• Анализ потока данных (Data Flow): Одно из главных преимуществ CPG – наличие ребер PDG, связывающих место определения переменной с её использованием. Пример запроса: “существует ли путь от входных данных пользователя (функция gets/read) до вызова system() без проверки/санитизации?”. Это классическая проверка уязвимости (инъекции). В SQL/PGQ мы можем задать шаблон пути в графе, начинающийся от узла вызова источника (метка, например, CALL с именем gets), проходящий по рёбрам передачи данных (REACHING_DEF/DATA_FLOW) и оканчивающийся узлом вызова sink-функции (system), с условием отсутствия промежуточного узла проверки (что можно учесть, исключив определённые узлы или добавив отрицательное условие). Выразительность: хотя SQL/PGQ – общий язык, он достаточно выразителен для таких шаблонов пути с условиями. Стандарт PGQ поддерживает фильтрацию и даже квантификаторы на пути. В CPGQL подобный запрос решается DSL-паттерном (cpg.call("gets").reachableBy(...) и фильтры), то есть концептуально аналогично. Однако, генерация кода: LLM, вероятно, увереннее сгенерирует SQL-подобный MATCH-запрос, чем воспроизведёт правильный вызов методов DSL Joern. Эффективность: DuckDB может победить за счёт оптимизированного поиска путей. Авторы DuckPGQ отмечают необходимость эффективных алгоритмов поиска путей в графе и уже реализовали компактное представление графа для этого[15]. В результате поиск по графу зависимостей в DuckDB выполняется конкурентно показателям специализированных решений, а для больших графов – даже быстрее за счёт агрессивных оптимизаций (как показали бенчмарки LDBC субграфов)[16].
• Анализ потока управления (CFG): Запросы, связанные с управляющей логикой – например, поиск всех путей исполнения, где переменная x может остаться неинициализированной, или определение, что ветка else отсутствует у ряда if – требуют обхода CFG. С PGQ можно использовать шаблоны вроде (a)-[:CFG*]->(b) для пути в CFG-графе, добавляя условия на свойства узлов a, b. Пример: найти все условные узлы IF без соответствующего узла ELSE (что может указывать на пропущенную ветку обработки) – выражается как выбор узлов типа IF, у которых нет исходящего ребра типа FalseBranch (условно) на блок else. В SQL это можно сделать либо графовым MATCH с опциональным паттерном, либо традиционным LEFT JOIN на таблицу ребер, проверяя NULL. В CPGQL аналогично: DSL позволяет переходить ifStmt.else и проверять существование. Обе парадигмы справляются, но LLM проще объяснить через стандартные SQL-понятия (join, null), если графовый синтаксис сложноват. Производительность: DuckDB легко выполнит такой запрос, т.к. это пара простых фильтраций по типам узлов и наличию связей – колонночное представление быстро отфильтрует миллионы узлов по типу.
• Поиск уязвимостей и паттернов безопасности: Благодаря единой модели CPG, можно комбинировать AST, CFG, PDG в одном запросе – это мощный инструмент для обнаружения сложных багов. Например, утечки памяти: запрос: найти функции, где выделяется память (вызов malloc/new), но отсутствует соответствующий вызов освобождения (free/delete). Это делается двумя подзапросами: (1) ищем узлы вызова malloc и берём идентификатор выделенного объекта, (2) проверяем, есть ли по графу данных путь, ведущий в вызов free с тем же указателем. SQL/PGQ может выразить это либо одним MATCH с двумя частями (связанный паттерн для malloc и отсутствующая дуга к free), либо двумя запросами с соединением результатов. CPGQL DSL предоставляет для подобных задач удобные цепочки (например, Joern имеет встроенные шаги .notCalled("free") и т.п. для простых случаев). Однако DSL ограничен предустановленными приёмами, тогда как SQL позволяет написать любой нужный запрос напрямую. Эффективность: и здесь DuckDB, обрабатывая данные колонками, масштабируется лучше. Отмечено, что графовые БД пока “молоды”, их производительность на аналитических запросах значительно ниже, чем у РСУБД[9]. В то же время, именно сочетание разных представлений (AST+CFG+PDG) делает поиск уязвимостей более результативным: оригинальное исследование CPG показало нахождение 10 из 12 известных уязвимостей в ядре Linux благодаря комбинированным обходам графа[17]. С DuckDB мы получаем то же богатство анализа, но на более зрелой платформе.
Сравнение с CPGQL (Joern DSL): CPGQL – это, по сути, специализированный язык запросов для кода (основанный на Scala/Gremlin у Joern[18]). Он предлагает удобные высокоуровневые методы (например, cpg.method.name("foo").caller) и знает схему CPG "из коробки". Это плюс для эксперта, но для LLM такой DSL малоизвестен. В отличие от этого, SQL/PGQ – стандартный и близок к языковым данным, на которых обучены модели. С точки зрения выразительности, SQL/PGQ покрывает практически все возможности: шаблонное сопоставление подграфов, навигацию по ребрам, фильтрацию свойств, агрегации (можно, например, посчитать число вызовов или среднюю глубину CFG-дерева функции и т.п.). Возможно, DSL Joern лаконичнее в некоторых местах (он “знает”, какие типы узлов существуют, можно писать cpg.file.extension(".cpp") и т.д. почти на естественном языке для безопасника). Но такой лаконизм достигается узкой привязкой к схеме. С точки зрения генерации кода LLM, преимущество у SQL/PGQ: он более универсален, и модель легче подкорректировать под синтаксис MATCH, чем учить десяткам методов Joern. Кроме того, LLM может пояснить или модифицировать SQL-запрос – язык SQL структурирован, понятен и хорошо подходит под “chain-of-thought”. DSL же может вызвать ошибки, если LLM не воспроизведёт точно методы API.
Итог по запросам: средства SQL/PGQ в DuckDB позволяют реализовать широкий спектр запросов к графу кода – от тривиальных выборок узлов по свойствам до сложных рекурсивных шаблонов поиска уязвимостей. Производительность на крупных кодовых графах, по имеющимся данным, либо не уступает специализированным CPG-движкам, либо превосходит их на сложных запросах[9]. При этом разработка запросов и их генерация LLM’ом упрощается благодаря использовании промышленного стандарта и мощи оптимизирующего SQL-движка.
3. Плюсы и минусы CPG на DuckDB, дополнительные сценарии использования
Ниже суммированы преимущества и недостатки подхода с реализацией CPG в DuckDB, а также рассмотрены дополнительные возможности, которые открываются в контексте ассистента на основе LLM + CPG.
Преимущества решения
• Единый стандарт и экосистема SQL – Использование SQL/PGQ избавляет от необходимости учить специализированный язык запросов. Индустриальный стандарт повышает понятность и переносимость решений. Отсутствие фрагментации языков запросов благоприятно для распространения графового анализа[7]. Кроме того, мы можем применять весь арсенал SQL: джоины, агрегации, подзапросы, функции. Например, легко объединить данные графа с другими таблицами (тесты, метрики качества кода и пр.) в одном запросе – то, что затруднительно в закрытых инструментах.
• Производительность и масштабируемость – DuckDB обеспечивает колонковое хранение, векторизированное выполнение и параллелизм, что даёт высокую скорость на запросах к графу даже при больших размерах кода[19][12]. В работах показано, что DuckPGQ масштабируется на графах соцсети LDBC в десятки миллионов ребер, превосходя многие нативные графовые движки по времени ответа[9]. Для анализа кода это означает способность быстро обрабатывать большие монорепозитории или кодовые базы с длительной историей. В RAG-сценарии, где важна скорость выдачи контекста LLM, такая эффективность – огромный плюс.
• Встроенные алгоритмы графового анализа – Реализация SQL/PGQ включает готовые механизмы для поиска путей, шаблонов, проверки обходов на ацикличность и т.д. Разработчики DuckPGQ отмечают, что они добавили алгоритмы many-source path-finding специально под графовые запросы[15]. Следовательно, сложные задачи (поиск всех путей между узлами, с определёнными ограничениями) не требуют нам самим писать рекурсивный код – СУБД возьмёт на себя оптимальный обход. Это уменьшает сложность реализации сценариев вроде поиска достижимости между событиями в коде, анализа зависимостей типов (например, находить все типы, от которых зависит данный тип, по цепочке импорта/наследования).
• Семантическое объединение данных – Хранение CPG в реляционном виде открывает дорогу к гибридному анализу. Мы можем, например, дополнить узлы графа столбцами с embedding (векторным представлением кода) и в одном SQL-запросе находить узлы по структурным признакам и сортировать их по косинусному сходству запроса разработчика. Это приближает нас к реализации действительно умного ассистента: он сможет выбирать кандидатов как по графовым связям (точно отвечая на структурные вопросы), так и по семантической близости к запросу. DuckDB уже сейчас поддерживает работа с векторами (через UDF) и легко интегрируется с Python, что позволяет осуществлять подобные комбинации.
• Отлаженность и совместимость – DuckDB – активно разрабатываемая open-source СУБД, с сообществом и тестированием. Используя её, мы избегаем проблем “самописного” хранилища. Все транзакционные аспекты, надёжность хранения, совместимость с CSV/Parquet – идут из коробки. Например, граф кода можно импортировать из Parquet-файлов, выполнить MATCH-запросы, а результаты сохранить обратно – всё одним инструментом. Инструменты визуализации (BI, Jupyter) также сразу совместимы (есть даже надстройки для визуализации графов DuckPGQ). Это проще, чем интегрировать, скажем, Neo4j или проприетарную DB в существующие пайплайны.
• Гибкость запросов и комбинирование свойств – В SQL/PGQ легко сочетать разные критерии (паттерны графа и атрибуты узлов). Например, можно запросом сразу отфильтровать по метаданным: "найти функции с меткой @Deprecated, которые не вызываются нигде" – MATCH-паттерн на графе вызовов + условие на свойство узла. Такой гибридный запрос будет лаконичен. В DSL это тоже возможно, но синтаксически может оказаться более громоздким, а в SQL это естественное сочетание WHERE с графовым MATCH. Для LLM, генерирующего ответ, чем меньше специальных конструкций – тем лучше.
Недостатки и возможные сложности
• Необходимость явного схемного соответствия – Реляционная модель требует определить схему таблиц под CPG (узлы разных типов, таблицы ребер с внешними ключами). Расширяемость может пострадать: добавление нового типа узла или свойства потребует ALTER TABLE или новую таблицу. В то время как графовые хранилища гибко хранят разнородные узлы и легко обогащаются новыми связями без изменения схемы[20]. Например, если в будущих версиях CPG добавят новый слой (скажем, граф зависимостей модулей), нам придётся менять структуру БД. Это увеличивает стоимость поддержки по сравнению с схематически гибким NoSQL-графом.
• Объём данных и накладные расходы – Представление всего кода в табличном виде может быть объёмным. CPG граф включает множество низкоуровневых узлов (каждый оператор, литерал – узел) и ребер. Хранить их в колонках DuckDB – эффективно по памяти благодаря сжатию, но при очень больших кодовых базах (сотни миллионов LOC) объём может стать проблемой. Специализированные движки (например, OverflowDB от ShiftLeft) оптимизированы именно под граф кода, хранят объекты в памяти с указателями, убирают избыточность. В DuckDB же данные более универсальны. Кроме того, транзиентность vs постоянство: по умолчанию property graph в DuckDB может создаваться как временный (в памяти)[21]. Хотя с версии 0.1.0 DuckPGQ поддерживается и сохранение графа[22], это пока новая функциональность. Есть риск, что при перезапуске сессии придётся пересоздавать граф, если не сохранить явно таблицы. В общем, нужно продумать стратегию хранения – либо генерировать CPG налету при запуске ассистента, либо хранить и обновлять его при изменениях кода.
• Ограничения текущей реализации SQL/PGQ – Стандарт молод, и DuckPGQ – активный проект. Пока не все возможности могут поддерживаться. Например, на момент публикаций DuckPGQ не реализованы UNION ALL для объединения путей внутри MATCH[23] и некоторые другие расширения. В контексте анализа кода это не критично, но нужно учитывать: возможно, потребуется обходить ограничения, формулируя запросы иначе. CPGQL DSL, напротив, специально заточен под анализ кода и может иметь “шорткаты” (например, мгновенный доступ к семантически важным узлам вроде “метод -> все его параметры” или “переменная -> место объявления”), тогда как в SQL/PGQ это надо явно связать по нескольким таблицам/ребрам. То есть в некоторых случаях запросы SQL будут более многословны, и их генерация/оптимизация ляжет на плечи LLM и разработчиков.
• Опыт команды и инструменты – У команды может просто не быть опыта глубокого тюнинга SQL для графовых задач. Специалисты по безопасности часто знакомы с Python-скриптами и DSL типа Joern, но не с написанием MATCH-запросов в SQL. Порог входа для новичков (не для LLM, а для людей) может повыситься, если SQL/PGQ пока мало распространён. Кроме того, экосистема инструментов статического анализа (те же Joern/Ocular) предоставляет готовые библиотеки шаблонов уязвимостей, накопленные исследователями. Перенеся CPG в DuckDB, мы эту экосистему теряем – придётся вручную воссоздавать некоторые запросы по описаниям. Это не технический минус платформы, но фактор, влияющий на сроки внедрения решения.
• Обратные ограничения LLM – Интегрируя LLM с БД, надо учитывать ограничения самой модели. Сложный SQL-запрос может превысить контекст или сбить модель. Нужно продуманно проектировать промпт: давать модели описание схемы графа, примеры запросов. Хотя SQL знаком, новый синтаксис PGQ (MATCH... ) может быть неизвестен модели, так как это новинка 2023 года. Возможно, потребуется fine-tuning или хотя бы несколько демонстрационных примеров, чтобы модель уверенно писала графовые запросы. И всё же, это решаемо (обучение куда проще, чем весь DSL с нуля).
• Опыт ShiftLeft: специально заточенные решения – Стоит отметить, что команда Joern отказалась от общего графового движка (Neo4j/Gremlin) из-за выявленных ограничений и создала собственный OverflowDB и DSL[18]. Это предупреждение, что универсальное решение может уступать оптимизированному. Например, OverflowDB хранит граф на диске с ленивой подгрузкой узлов, поддерживает инкрементальное обновление, работает в распределённом режиме – всего этого DuckDB не даёт (DuckDB – in-process библиотека, масштабирование горизонтальное не предусмотрено). Значит, для очень больших проектов (миллионы компонентов, частые изменения) может возникнуть проблема: обновление графа означает перерасчёт и загрузку в DuckDB заново. В специализированных инструментах есть incremental анализ (добавить только изменённые файлы). В нашем случае, мы либо принимаем overhead переиндексации, либо придумываем синхронизацию (что непросто в SQL). Таким образом, минус – потенциально меньшая гибкость под задачи непрерывного анализа (CI/CD).
Дополнительные сценарии использования CPG+DuckDB в ассистенте LLM
Основной сценарий, о котором мы говорили, – это “копилот” для разработчиков, отвечающий на вопросы по коду с помощью RAG (запрос к базе знаний + генерация ответа). При наличии CPG в DuckDB открываются и смежные возможности в рамках этого сценария:
• Автоматическое обнаружение уязвимостей и предупреждение разработчика: Ассистент может не только отвечать на прямые вопросы, но и проактивно анализировать код на уязвимые конструкции. Имея CPG, можно запускать периодические SQL-запросы-паттерны (или триггерить их при изменениях в репозитории) – например, искать небезопасные вызовы, несанитизированные входы, утечки ресурсов. Результаты (список подозрительных мест с объяснениями) LLM может превратить в комментарии к Pull Request или в отчёт. Реализовать это можно как набор хранимых шаблонных запросов в DuckDB. Пример реализации: хранить библиотеку запросов (возможно, даже как представления CREATE VIEW VulnerablePatternX AS SELECT ... FROM GRAPH_TABLE ...), а LLM-туллинг будет их запускать и интерпретировать результат. Такой подход объединяет статический анализ (как в CodeQL) с LLM, который может давать человеку понятные обоснования каждому найденному случаю.
• Глубокое понимание архитектуры и зависимостей: CPG содержит связи между файлами, модулями, типами (например, узлы FILE с ребром CONTAINS для функций, или узлы TYPE с ребром наследования). LLM-ассистент может отвечать на вопросы вроде «Как модуль X зависит от модуля Y?» или «Какие компоненты использует класс Z?», выполняя соответствующие графовые запросы. Дополнительно можно строить диаграммы: выгрузив результаты запросов (например, матрицу зависимостей) и используя библиотеку графов, ассистент способен сгенерировать визуализацию (функциональность DuckPGQ + DuckGraphViz уже это допускает). Разработчик получит не только текстовое объяснение, но и граф связи классов или вызовов. Это реализуется комбинированием SQL-запроса и генерации изображения (через Python-ноутбук или web-интерфейс бота). В данном случае CPG на DuckDB выступает как хранилище знаний об архитектуре: например, можно заранее вычислить и сохранить граф зависимостей пакетов, и LLM будет просто извлекать нужный срез.
• Поиск дублированного или схожего кода (clone detection): На основе CPG можно выявлять потенциальные дубликаты функций или участков – для этого подходят как графовые изоморфизмы, так и embedding. Схема реализации: для каждой функции сохраняем некоторый структурный идентификатор (например, абстрагированный граф потока или просто AST-поддерево без имён) и ищем совпадения. SQL/PGQ может помочь найти функции с одинаковым шаблоном AST (MATCH-паттерн, где определённая структура повторяется). Такая задача тяжела для LLM напрямую (ему надо прочесть весь код), зато база CPG может выловить кандидатов практически моментально. Ассистент потом либо сообщает “Функции A и B очень похожи”, либо при вопросе «Есть ли повторяющийся код, который стоит вынести?» уже знает кандидатов. Реализовать можно хранением канонизированных AST в строковом виде и банальным SQL GROUP BY с COUNT, либо специальным графовым запросом на изоморфизм подграфов (хотя последний может быть ресурсоёмким). Тем не менее, даже простейшее приближение – совпадение последовательностей API-вызовов – легко делается SQL-запросом по графу вызовов.
• Оценка метрик и качеств кода: Имея полное представление программы, несложно вычислять метрики: цикломатическая сложность (через подсчёт ветвлений в CFG), степень зацепления модулей (через граф вызовов/зависимостей), количество параметров функций, плотность комментариев и пр. Вместо вручную написанных анализаторов, можно несколькими SQL-запросами получить таблицу метрик по всем функциям/классам. LLM-ассистент может использовать это для ответов: «Какие функции самые сложные в проекте?» – просто выбираем топ по сложности; «Есть ли в модуле X функции с более чем N параметрами?» – запрос по свойству. Такие отчёты DuckDB сгенерирует мгновенно, а LLM обернёт в читабельный вывод (вплоть до рекомендаций). Прелесть в том, что SQL объединяет сбор данных и агрегацию: можно одной командой посчитать все требуемые показатели без пост-обработки. В DSL тоже можно, но чаще пришлось бы выгружать и обрабатывать скриптами.
• Комбинирование с динамическим анализом и тестами: Хотя CPG – статическая модель, ассистент мог бы связывать её с результатами выполнения. Например, зная из CPG, какие функции могут логически вызываться из main, LLM может при запуске тестов приоритизировать определённые пути. Или наоборот, если есть профили выполнения (время работы функций), можно обогатить граф узлами “горячих точек” и спрашивать: «Какие части кода чаще всего исполняются и связаны ли они с модулем Х?». DuckDB как универсальная БД может хранить и профайлинг, и связывать по именам функций с графом. LLM сможет ответить на такие междисциплинарные вопросы (например, “Этот медленный код – он критичен для безопасности?” – проверив, что “медленный код” касается функций шифрования, можно сделать вывод).
Подводя итог, реализация CPG в DuckDB даёт богатую почву для расширения возможностей ассистента разработчика. Она объединяет проверенные техники статического анализа с силой LLM, облегчающей интерпретацию результатов. Плюсы такого подхода – в скорости, стандартизации и интегрируемости – делают его перспективным для практического применения. Однако, необходимо учитывать и минусы: схема требует поддержки, не все графовые запросы тривиальны в SQL, а для очень тонких анализов могут понадобиться дополнительные оптимизации. В целом же, сравнительный анализ показывает, что выразительность и простота генерации запросов через LLM выше в случае SQL/PGQ, чем в случае узкоспециализированного CPGQL, при сопоставимой мощности анализа. Это подтверждается и трендом стандартизации графовых запросов: индустрия движется к тому, чтобы графовые представления (включая CPG) были доступны средствами привычных СУБД, объединяя лучшее из двух миров[24][3].
